# MineClone → Asteria: deep source parity audit

**Audited:** 2026-10-14. **Asteria source baseline:** `030c78377445b502e55ccf766f366389de1eb9ae` (subsequent `main` changes through `815ea6cf5` were checked for affected paths). **MineClone source references:** `main` `a4e9d00dafd384ae0086e30f684c7`; `world-systems-rebuild` `e8bc8562abc22eb4a54561c1e7afe8cc086e3dd9`. The investigation is **source/commit/content comparison only**; neither executable was interactively played and no in-engine side-by-side capture was taken.

## Verdict

The broad port architecture and feature inventory are substantially present, but **functional parity cannot yet be signed off**: several movement semantics and at least one Survival loot outcome differ **in current source**, independently of unfinished visual QA. These are narrow bugs/content mismatches, **not** an instruction to re-port whole subsystems. Avoid repeating the completed port batches enumerated in [the reconciled ledger](MINECLONE_PORT_REMAINING.md).

### Authored visual differences (not automatically functional defects)

| Finding | Source evidence | Required decision |
| --- | --- | --- |
| **OBJ-01: lighting and shadows** | MineClone's ten original `data/objects/*.json` all explicitly opt out of shadow casting/receiving (for example `grass`, `mushroom_blue`, `mushroom_brown`, `pebble`, `stick`). Their Asteria equivalents frequently omit these fields; `ObjectDefinitionJson` defaults `castsShadow` **true** and `receivesShadow` **true**. Asteria `grass.unlit=false` vs MineClone `true`; several mushrooms similarly differ. | Distinguish the project's intentional requirement that Objects respond to light and cast/receive shadows from an undesired visual divergence. **Do not blindly restore MineClone's unlit/shadow-off flags.** Compare real rendering first. |
| **FLUID-01: water appearance/spread** | MineClone `data/fluids/water.json`: opacity 0.32, roughness 0.18, light dampening 2, spread speed 16. Asteria authored water: opacity 0.72, roughness 0.15, light dampening 1, spread speed 5, and a texture-based Godot presentation. | These are real authored-data differences; their visual/runtime equivalence is **not established** because rendering and spread scheduling are implemented differently. Decide deliberate art/balance differences after fixed-scene screenshots and spread tests; do not equate JSON values alone with a bug. |
| **UI-01: deliberate layout/extensions** | Asteria separates Controls from Game Settings, extends menu with Packs/Mods, uses generic localized player name rather than MineClone `Yogg'Sara`, and adapts Sphere/biome HUD. Its inventory **already displays Crafting above Inventory**, matching current MineClone. MineClone's current Starting Screen **does not** contain a language selector. | Keep intentional extensions; only change if the product design requires it. The earlier roadmap statements about a language selector and inverse crafting order were stale/incorrect. |
| **PORTAL-01: storage adaptation** | MineClone writes a portal face **Layer** in empty space; Asteria uses the existing centered Layer-shaped, noncollidable portal **block**, carrying destination metadata. Frame detection, traversal, arrival structure, surface staircase and persistence are connected. | Deliberate internal architecture. Verify traversal and appearance natively; no new Layer storage subsystem is justified merely to mirror Rust types. |

### Areas cross-checked without a confirmed missing port

- **Creatures:** compared **all 20 same-named JSON definitions** under `data/creatures` and `packs/default/data/creatures`. Every original top-level key/value remained equal in the source snapshot; Asteria **adds** `lootTable`, `contactDamage`, `rangedAttack`, or `naturalSpawn` rather than omitting authored source fields. Behavior and native animation remain subject to acceptance; the additional attack systems are already implemented, not new missing ports.
- **Core combat/projectiles:** punch `damage=1`, knockback chance 1, strength 0.75 match in authored `data/attacks/punch.json`. Asteria owns existing creature knockback, pursuit, ranged projectile and swept collision; no missing combat engine was established by this pass.
- **Items/tools/crafting:** MineClone's base nine tools and Asteria's nine authored tools are present with **renamed files/IDs** (for example `rustic_hatchet.json` vs `hatchet_rustic.json`). Corresponding hatchet recipe keeps 2 pebbles + 3 sticks + 2 fiber; names/asset paths are adapted. The concrete grass-fiber drop gap above is about **acquisition**, not recipe execution.
- **World/portals/Objects:** World Load/Delete/Recreate, save on exit, Flat/Void, object occupancy/interaction/pickup/loot runtime, portals' authored return structures and surface connections, StructureSet placement and World Tree variants have current implementations. Do not classify differences in storage model, asset IDs or authoring schema alone as missing gameplay.
- **UI/interaction:** chat focus/ESC/OS-refocus, inventory right/Shift actions, independent Creative scrolling, controls and localized target HUD have been addressed in recent commits and automated browser/native smoke. Their remaining question is a **reproducible running-client discrepancy**, not re-implementation.
- **Resource inventory:** direct filename comparison is misleading after Asteria's **type-first ID rename** and extensive new content. MineClone's `river_ocean_mouth` and some StructureSet definitions are not one-to-one filenames; feature-specific worldgen is excluded from the port parity milestone until a requested concrete discrepancy is demonstrated.

## Release / parity sign-off gate

1. Correct or explicitly approve the **confirmed gameplay differences** (LOOT-01 and MOVE-01 through MOVE-06). Prioritize LOOT-01 and MOVE-01, then the remaining movement policy together.
2. Run targeted Core and Godot movement tests plus actual stair, swim, flight, water-surface, landing and drop-pool scenarios in a real client.
3. Perform a same-seed cross-client acceptance of portal round-trip, save → app quit → fresh-process load, Object interaction, equipment and creature damage, on the already-implemented runtimes.
4. Compare MineClone `main` and embedded Godot/WRY screenshots for Objects, underwater rendering, player/HUD, inventory, day/night, and focus at fixed viewports. Mark **observed defects only**.
5. Distinguish `source parity completed`, `behavior parity accepted`, and `visual/runtime QA accepted`; never mark all three completed from repository contents alone.

**Decision:** the port foundation is largely complete, but **full gameplay equivalence is not yet demonstrated**. The next **implementation** batch should fix only the concrete movement and grass-fiber discrepancies above; there is no justification to rebuild inventory, portals, WebUI or creature systems.

## Second gameplay batch — 2026-10-14

After `87523b4` restored grass's fiber loot and one-shot grounded jumping, the next batch changes flight acceleration/deceleration to the authored 75/90, terminal falling speed to -25, and water movement to MineClone's buoyancy (+0.6), ascend (+3.8), descend (-3), near-surface target (+7), acceleration (12) and horizontal walking dynamics. The new `PlayerMovementPhysics` is a pure Core calculation used by the existing Godot physics owner. All changes have focused regression tests.

**Source correction is not yet embedded runtime acceptance.** MOVE-04 (0.5-block step behavior) and MOVE-06 (player collider/camera dimensions) still require Godot-specific investigation and native collision verification; do not blindly replace physical dimensions.
